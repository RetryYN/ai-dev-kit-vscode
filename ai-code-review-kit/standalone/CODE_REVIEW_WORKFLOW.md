# 6段階コードレビュー ワークフロー設計書

AIと人間の境界線を「問題の性質」で切り分けるコードレビュー運用フレームワーク。
出典の元記事（Zenn「コードレビューを6段階にしたら、AIと人間の分業が見えた」）の6段階モデルをベースに、2026年5月時点の最新ツール動向とベンチマークで情報補強した実務運用版。

最終更新: 2026-05-24

---

## 1. 設計思想

コードレビューは「AIが上から降りていく」のではなく、**段階ごとに問題の性質が変わる**。
Format には一意の正解があり、Architecture には正解がない（未来予想になる）。
正解が一意でなくなるほど、AI比率は下がり、人間の責任比率が上がる。

```
正解が一意    ←──────────────────────────────→    正解が存在しない
Format    Lint    Style    Logic    Design    Architecture
100% AI   100%AI  90%AI    60%AI    30%AI     0% AI
```

3層モデル（自動ゲート / AIレビュー / 人間レビュー）が「誰が何を見るか」の設計図だとすれば、
6段階は「どこに人間の集中力を残すか」の解像度を上げた寸法図にあたる。

---

## 2. 6段階の定義

AI比率は実務上の**目安**であり、チーム・言語・ツールの世代で揺れる（定量基準にはしない）。

| 段階 | 対象 | AI比率 | 人間比率 | ゲート性質 | 主なツール（2026年版） |
|------|------|--------|----------|------------|------------------------|
| 1 | Format | 100% | 0% | ブロッキング | pre-commit hook, Prettier, gofmt |
| 2 | Lint | 100% | 0% | ブロッキング | ESLint, Ruff, mypy, tsc |
| 3 | Style | 90% | 10% | 非ブロッキング | CodeRabbit, GitHub Copilot Code Review |
| 4 | Logic | 60% | 40% | 条件付きブロッキング | Claude Code `/review`・`/ultrareview`, CodeRabbit |
| 5 | Design | 30% | 70% | レビュー会話 | ペアレビュー + AI機械的ヒント |
| 6 | Architecture | 0% | 100% | 事前設計 | ADR + テックリードのファシリテート |

### 段階境界の判定基準

- **Format / Lint の分離**: Format は「見た目」の規約（壊れても動く）、Lint は「意味」の規約（壊れたら動かない／将来動かなくなる）。pre-commit が重くなった時に「どちらを外すか」を判断できるよう分けておく。
- **Style と Logic の境界**: 命名・可読性は Style、振る舞いの正しさは Logic。
- **Logic と Design の境界**: 「このコードは正しく動くか」が Logic、「この責務はこのクラスに置くべきか」が Design。
- **Design と Architecture の境界**: コードの内側の構造が Design、システム境界・データフロー・認証範囲・デプロイ単位が Architecture。

## 3. 各段階の運用

### Stage 1: Format（100% AI / ブロッキング）

インデント・空白・改行コード・末尾セミコロン。pre-commit hook で機械的に処理する。
人間の判断は一切不要。レビューコメントで「インデントが揃っていない」を指摘している状態は、レビュアーの消耗を意味するので即ツール化する。

- ゲート: commit 時に整形チェック。不一致なら自動整形してステージし直すか、commit を止める。
- 担当: ツールのみ。

### Stage 2: Lint（100% AI / ブロッキング）

未使用変数・到達不能コード・暗黙の型変換。静的解析で検出する。

- ゲート: pre-commit + CI。エラーは PR をブロックする。
- 担当: ツールのみ。

> Stage 1–2 は「PR にすら到達させない層」。ここを hooks で固めるだけで、レビュアーの定型指摘時間を構造的にゼロにできる。

### Stage 3: Style（90% AI / 10% 人間 / 非ブロッキング）

命名・関数の分割粒度・コメントの過不足・可読性。

- AI が指摘を出し、人間は「採用／却下」だけを判断する。
- 却下する時は理由を一行残す。`.coderabbit.yaml` などプロジェクト固有ルールに反映できれば次回以降の精度が上がる。
- ゲート: 非ブロッキング（マージは止めない）。
- 担当: AI 主導、人間が最終承認。

### Stage 4: Logic（60% AI / 40% 人間 / 条件付きブロッキング）★最重要

N+1、SQLインジェクション、未処理例外、明らかなエッジケース。AIはこの辺りまでは検出する。
ただし**バグ検出のrecallは現状でも半分強**（後述ベンチマーク参照）。仕様書を見ていないAIは、コードベース内の整合性しか見られないため、「仕様由来のエッジケース」を取りこぼす。

#### 運用の核心（逆説ルール）

```
AIが指摘した部分 → AIに任せる
AIが指摘しなかった部分 → 人間が念入りに見る
```

- AIのコメントが多いPRほど、人間レビューは短く済む。
- **AIのコメントがゼロのPRこそ、仕様書を開いて時間をかけて読む価値がある。**
- 「AIが問題なしと言った」は、人間がスキップする理由には**ならない**。

Stage 4 が最も危険なのは、AIカバー率が60%という「中途半端な高さ」だから。
0%なら人間が全部見る、100%ならAIに任せる。60%は「7割は大丈夫だろう」という油断を生む。
中間ゾーンこそ人間の集中力を最も投下する。

- ゲート: critical（セキュリティ・データ整合性）は条件付きブロッキング、それ以外は非ブロッキング。
- 担当: AI と人間の協働。仕様判断の最終責任は人間。

### Stage 5: Design（30% AI / 70% 人間 / レビュー会話）

責務分割・APIの境界・依存関係の方向。

- AIに期待するのは機械的ヒントのみ（例:「この関数は150行あります。分割を検討してください」）。
- 「このパターンを増やすべきか減らすべきか」の方向性判断はAIにできない。AIは学習データ内の「平均的な良い設計」に寄せがちで、コードベース固有の制約（例: マルチテナントDBで Service 層は必ず `tenant_id` を受け取る、等）を読まない。
- 2人ペアレビューが効く。1人だと「自分の好み」を「設計判断」と取り違える。
- ゲート: レビュー会話で合意形成。
- 担当: 人間主導、AIは補助。

### Stage 6: Architecture（0% AI / 100% 人間 / 事前設計）

システム境界・データフロー・認証の責任範囲・デプロイ単位。

- アーキテクチャ判断は「正解」ではなく「未来予想」。3年後の成長・チーム拡大・ピボットに対し、AIはもっともらしい答えを出せても**責任を取れない**。
- これは PR レビューではなく**設計会議**。PR の前にやる作業。ADR（Architecture Decision Record）を書き、テックリードがファシリテートして議論する。
- ゲート: PR前のADR承認。PRレビューでは「ADRと整合しているか」だけ確認すればよい。
- 担当: 人間（シニア／テックリード）のみ。

#### 文章化による「AI比率の上昇」現象

ADRを書いた瞬間、Stage 6 の一部が Stage 5・Stage 4 に降りてくる。
「ADRと整合しているか」は機械的にチェックできるため、AIに委譲できる範囲が広がる。
**暗黙のチーム合意を明文化する投資が、そのままAIに任せられる領域を拡大する。**
これは設計プロセスへの投資判断に直結する重要な性質。

## 4. Approve 判断フロー

3層モデル時代の Approve は「Format OK / AI OK / ざっと見た」の3点セットだった。
6段階運用では、Approve を押す前に**どの段階まで責任を持っているか**を自問する。

```
[ ] Stage 1 Format     : 自動ゲート通過
[ ] Stage 2 Lint       : 自動ゲート通過
[ ] Stage 3 Style      : AI指摘に同意 or 却下理由を記録
[ ] Stage 4 Logic      : 仕様書と照合してエッジケースを確認した
                         （特にAIコメントがゼロの箇所を念入りに）
[ ] Stage 5 Design     : 責務分割に違和感がない／ペアで合意
[ ] Stage 6 Architecture : 事前ADRと整合している
```

このチェックを通った Approve は重みが増す。
Logic と Design に不安があれば「Approve しない選択」をしやすくなり、「とりあえずLGTM」が出にくくなる。

## 5. AIレビューツールの実力（2026年5月時点ベンチマーク）

AIに任せる範囲を決めるための前提データ。数値はツール世代で陳腐化が早いため、四半期ごとに見直す。

### バグ検出精度（独立ベンチマーク）

- Macroscope 48% / CodeRabbit 46% / Cursor BugBot 42% / Greptile 24%（Macroscope調べ）
- 従来型の静的解析（SAST）は20%未満
- 別のベンチマークでは Greptile が catch rate 82% だが false positive が多い（1回あたり11件 vs CodeRabbit 2件）

### F1 / recall（CodeRabbit vs Copilot）

- CodeRabbit: F1 51.5% / recall 52.5%
- GitHub Copilot: F1 44.5% / recall 36.7%

### セキュリティ脆弱性（OpenSSF CVE Benchmark）

- CodeRabbit: accuracy 59.39% / F1 36.19%（実脆弱性の約41%を取りこぼす）

**結論**: Logic 層は「6割見つかれば上等」が現状の感覚。半分以上は見逃す前提で、Stage 4 の逆説ルールを運用する。精度を追うほど false positive（ノイズ）が増えるトレードオフがあるため、recall一辺倒では選ばない。

## 6. Claude Code レビュー3経路の使い分け

Claude Code には2026年時点で3つのレビュー経路がある。Stage 4 の実行手段として使い分ける。

| 経路 | 対象プラン | 仕組み | コスト | 特性 | 推奨用途 |
|------|-----------|--------|--------|------|----------|
| 自作サブエージェント | 任意の有料 | `.claude/commands/` に slash command、複数サブエージェント並列 | APIトークンのみ | ローカル実行・カスタム可、提案の約75%がactionable | 日常のローカルレビュー、Stage 3–4 |
| `/ultrareview` | Pro / Max | クラウドのマルチエージェントbug hunter | 約 $5–20 / run | 検証済みバグのみ報告、research preview | リリース前の重点Logicレビュー |
| 公式 Code Review | Team / Enterprise | GitHub統合（5ステップ）、マネージド | 約 $15–25 / review | false positive < 1%、結果まで約20分 | PR自動レビューの恒常運用 |

補足:
- サブエージェントは `.claude/agents/`（プロジェクト）または `~/.claude/agents/`（個人）に置き、最大10並列。`per-agent model` 指定で高stakes推論を Opus、高volume処理を Haiku に振り分けるとコスト最適化できる。
- 単一エージェントのレビューより、複数エージェントで角度を変えるほうが見落としが減る（actionable率が50%未満→75%程度に向上する報告あり）。
- それでも**仕様判断の最終責任は人間**。AIのレビューは Approve の根拠にしない。

## 7. チーム導入ステップ

いきなり6段階を全部入れると挫折する。即効性のある層から順に固める。

1. **Stage 1–2 を hooks で固める**（1日で完了・即日効果）
   `scripts/precommit-gate.sh` を導入し、Format と Lint を commit 前に強制する。
2. **Stage 3 に AIレビューを入れる**（1週間慣らす）
   CodeRabbit か Copilot Code Review を PR に接続。Copilot契約があれば追加費用なし。
3. **Stage 4 のための仕様書整備**（最も時間がかかる・最重要投資）
   AIが見られない「仕様由来のエッジケース」をまず人間が明文化する。ここが詰まると Logic 層がAI任せになる。
4. **Stage 5–6 をチーム文化として育てる**（仕組み化より習慣化）
   ペアレビューと ADR。`assets/agents/` のサブエージェント定義を共有して Stage 4–5 を半自動化する。

## 8. 運用KPI（任意）

導入効果を測る指標の例。

- レビュアーの定型指摘時間（Stage 1–3 起因のコメント数）→ ゼロを目指す
- Stage 4 起因の本番バグ流出件数 → 仕様書整備で逓減
- 「AIコメントゼロPR」に対する人間レビュー所要時間 → 短すぎる場合は逆説ルールが機能していない警告
- Approve から本番障害までのリードタイム
- ADR化された決定の割合（高いほど Stage 6 の一部がAI委譲可能に）

## 9. アンチパターン

- **「AIが見ているから自分は見なくていい」**: Stage 4 で最も起きやすい認知のショートカット。逆説ルールで構造的に防ぐ。
- **AI比率の数値を定量KPIにする**: 目安であって基準ではない。言語・ツール世代で揺れる。
- **Architecture を PR レビューで揉める**: 「認証を各サービスに置くか Gateway に集約するか」を PR で議論すると地獄になる。事前ADRで決める。
- **recall一辺倒でツール選定**: false positive が多いとPRがノイズで埋まり、開発者が無確認でコメントを解決し始める。signal-to-noise を見る。
- **却下理由を残さない Style レビュー**: 次回のAI精度が上がらず、同じ指摘が繰り返される。
