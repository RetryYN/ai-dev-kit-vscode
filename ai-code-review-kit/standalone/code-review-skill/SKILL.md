# 6段階コードレビュー スキル

コード変更を6段階に分けてレビューする。各段階は「問題の性質」が異なり、AIが担える比率が段階的に下がる。
このスキルの目的は、AIが得意な段階を機械的に処理しつつ、**AIが取りこぼす段階（特にLogicの仕様由来エッジケースとDesign/Architecture）に人間の判断を集中させる**こと。

## 基本原則

1. AIは「正解が一意な段階」を担い、「正解が存在しない段階」には踏み込まない。
2. Logic層では逆説ルールを適用する: **AIが指摘した箇所はAIに任せ、AIが指摘しなかった箇所こそ念入りに見る。**
3. 「テストが通っている」「コードとして整合している」は、仕様が正しいことを意味しない。仕様判断の最終責任は人間にある。
4. Approveの根拠に「AIが問題なしと言った」を使わない。

## ワークフロー

### Step 0: スコープ特定

レビュー対象を以下の優先順で決める。

1. ユーザーが明示した範囲（ファイル・PR番号・コミット範囲）
2. ステージ済み差分（`git diff --staged`）
3. 直近のコミット差分（`git diff HEAD~1`）またはブランチ差分（`git diff main...HEAD`）

仕様書・設計ドキュメント・ADR・既存の命名規則ファイル（`.coderabbit.yaml`, `CONTRIBUTING.md`, `CLAUDE.md` 等）があれば読み込み、判断の基準にする。
**仕様書が見当たらない場合は、その旨を明記する**（仕様由来のエッジケースは検出できないと宣言する）。

### Step 1: Stage 1–2（Format / Lint）

機械的な層。手動でコメントせず、ツールに委ねる前提で確認する。

- 整形ツール（Prettier / gofmt / black 等）と静的解析（ESLint / Ruff / mypy / tsc 等）の設定があるか確認する。
- 設定がある場合: `scripts/precommit-gate.sh` 相当のチェックが通る前提で、Format/Lint起因の指摘は**しない**。
- 設定がない場合: 「Stage 1–2 が自動化されていない」ことだけを指摘し、導入を提案する。個別のインデント・未使用変数の指摘でレビューを埋めない。

### Step 2: Stage 3（Style）

命名・関数分割の粒度・コメントの過不足・可読性。

- 指摘は出すが、各指摘に「採用推奨／任意」のラベルを付ける。
- プロジェクトの命名規則ファイルがあればそれに照らす。なければ「コードベース全体の規則を確認すべき」と注記する。
- 非ブロッキング。マージを止める理由にはしない。

### Step 3: Stage 4（Logic）★最も時間をかける

振る舞いの正しさ。N+1・SQLインジェクション・未処理例外・境界条件・並行性・リトライ条件・null/空配列の扱い。

実行手順:

1. まず差分から**機械的に検出できるバグ候補**を洗い出す（AIが見つけられる60%）。各々に根拠を付ける。
2. 次に**仕様書と照合**する。コードベース内では整合していても仕様と食い違う箇所を探す。典型例:
   - 空配列・null・ゼロ件の扱い（仕様では「スキップ」なのにコードは「処理する」等）
   - 外部APIのリトライ条件（仕様では「429のみ」なのにコードは「5xx全部」等）
   - ページネーション・境界での1件ずれ
   - タイムゾーン・丸め・通貨・単位の暗黙の前提
3. **逆説ルールの適用**: 差分の中で「自分が何も指摘できなかった箇所」を明示的にリストアップし、そここそ仕様書を開いて念入りに確認する。AIコメントがゼロの領域は油断ポイントとして扱う。
4. critical（セキュリティ・データ整合性・課金・認証）に該当する指摘は「ブロッキング」と明記する。

複数観点で角度を変えて見る（入力検証・状態遷移・エラー経路・並行アクセス）。Claude Code環境ならサブエージェント並列レビュー（`assets/agents/` 参照）の利用を提案してよい。

### Step 4: Stage 5（Design）

責務分割・APIの境界・依存方向。

- AIとして出すのは機械的ヒントに留める（例: 関数が長すぎる、循環依存の疑い、責務の混在）。
- 「このパターンを増やすべきか減らすべきか」という方向性は**断定しない**。「既存パターンと揃えるべき／2人で合意すべき」と人間判断に委ねる。
- コードベース固有の制約（マルチテナント、レイヤ規約等）を読み取れた範囲で照合し、読めない部分は「ローカルルールの確認が必要」と注記する。

### Step 5: Stage 6（Architecture）

システム境界・データフロー・認証範囲・デプロイ単位。

- ここはレビューしない。判断は事前のADRと設計会議で行うべき領域。
- 差分がアーキテクチャに触れている場合（新しいサービス境界、認証フローの変更、データフローの変更等）は、「これは Stage 6 相当。PRレビューではなくADRで事前に決めるべき決定が含まれている」と**警告する**だけに留める。
- 既存ADRがあれば「ADRと整合しているか」だけを機械的に確認する。

### Step 6: Approve判断サマリ

最後に、ユーザーがApproveを押す前のチェックリストを提示する（`references/stage-playbook.md` のテンプレート参照）。
各段階について「確認済み／要確認／対象外」を明示し、Logic・Designに未確認が残る場合は「Approveを保留すべき」と伝える。

## 出力フォーマット

```
## レビュー結果: <対象>

### サマリ
- ブロッキング指摘: N件
- 非ブロッキング指摘: M件
- 仕様書: あり / なし（なしの場合は仕様由来エッジケース未検証と明記）

### Stage 3 Style（任意）
- [採用推奨] <ファイル:行> <指摘>
- [任意] ...

### Stage 4 Logic（最重要）
- [ブロッキング] <ファイル:行> <指摘と根拠>
- [要確認] <仕様照合が必要な箇所>
- ⚠️ AI指摘ゼロだった箇所（要人間確認）: <列挙>

### Stage 5 Design
- [ヒント] <機械的な観点>
- [人間判断] <方向性を要合意の箇所>

### Stage 6 Architecture
- ⚠️ ADRで事前決定すべき変更: <あれば列挙、なければ「該当なし」>

### Approve判断
[ ] Stage 1-2 自動ゲート / [ ] Stage 3 / [ ] Stage 4 仕様照合 / [ ] Stage 5 / [ ] Stage 6 ADR整合
→ 推奨: Approve可 / 条件付き / 保留
```

## 参照ファイル

- `references/stage-playbook.md` — 各段階の詳細チェックリストとApprove判断テンプレート。Logic層の仕様照合観点を網羅したい時に読む。
- `references/claude-code-paths.md` — Claude Codeのレビュー3経路（自作サブエージェント／`/ultrareview`／公式Code Review）の使い分け。実行手段を選ぶ時に読む。
- `scripts/precommit-gate.sh` — Stage 1–2（Format/Lint）を commit 前に強制するフック。導入を提案する時に使う。
- `scripts/review_report.py` — レビュー指摘を6段階で集計しMarkdownレポート化するスクリプト。
- `assets/agents/` — Claude Codeサブエージェント定義（logic-reviewer / design-reviewer / security-reviewer）。Stage 4 の並列レビューを設定する時に配布する。

## 注意

- AI比率（60%等）は目安であって定量基準ではない。数値で機械的にゲートしない。
- Format/Lint起因の指摘でレビューを埋めない。それはツールの仕事。
- 仕様書がない状態で「バグなし」と断定しない。「コードベース内では整合」と「仕様通り」は別。
