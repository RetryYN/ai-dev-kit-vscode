# Stage Playbook — 各段階の詳細チェックリスト

6段階レビューの各段階で「具体的に何を見るか」を網羅したプレイブック。
SKILL.md のワークフローを実行する際、特に Stage 4（Logic）で取りこぼしを防ぎたいときに参照する。

---

## Stage 1: Format チェックリスト

ツールに委ねる。人間・AIが個別に指摘しない。

- [ ] 整形ツール（Prettier / gofmt / black 等）の設定がリポジトリにある
- [ ] pre-commit / CI で整形チェックが走る
- [ ] 設定がない場合のみ「Stage 1 が未自動化」を1回だけ指摘し、導入を提案

---

## Stage 2: Lint チェックリスト

ツールに委ねる。

- [ ] 静的解析（ESLint / Ruff / mypy / tsc / go vet 等）の設定がある
- [ ] Lint エラーが CI で PR をブロックする
- [ ] 設定がない場合のみ「Stage 2 が未自動化」を1回だけ指摘

---

## Stage 3: Style チェックリスト

各指摘に「採用推奨／任意」のラベルを付ける。非ブロッキング。

- [ ] 命名: コードベース全体の命名規則と一致しているか（規則ファイルがあれば照合）
- [ ] 関数の分割粒度: 1関数が単一の責務か
- [ ] コメント: 過不足ないか（自明なコメント / 説明不足）
- [ ] 可読性: マジックナンバー、深いネスト、わかりにくい三項演算子
- [ ] 却下時は理由を一行残す（次回のAI精度向上のため）

---

## Stage 4: Logic チェックリスト ★最重要

### フェーズA: AIが機械的に検出できる層（約60%）

- [ ] N+1 クエリ
- [ ] SQL/コマンド/XSS インジェクション
- [ ] 未処理の例外・エラーの握りつぶし
- [ ] null / undefined 参照
- [ ] 明らかなオフバイワン
- [ ] リソースリーク（ファイル・接続の未クローズ）
- [ ] 競合状態・デッドロックの明らかな兆候

### フェーズB: 仕様書と照合する層（AIが取りこぼす）

コードベース内では整合していても、仕様と食い違う箇所を探す。

- [ ] **空・null・ゼロ件の扱い**: 「空配列ならスキップ」が仕様なのに処理していないか
- [ ] **外部APIのリトライ条件**: 「429のみ」が仕様なのに「5xx全部」になっていないか
- [ ] **ページネーション境界**: 1件ずれ、最終ページの扱い、カーソルの重複
- [ ] **タイムゾーン**: UTC / ローカルの混在、夏時間
- [ ] **丸め・桁**: 通貨の丸め方向、小数点以下の扱い、単位の前提
- [ ] **状態遷移**: 許可されていない遷移、冪等性、二重実行
- [ ] **境界値**: 上限・下限、最大文字数、ゼロ・負数
- [ ] **権限・テナント**: 他テナント/他ユーザーのデータにアクセスできないか

### フェーズC: 逆説ルールの適用

- [ ] 差分の中で「自分が何も指摘できなかった箇所」を列挙した
- [ ] その箇所について仕様書を開いて念入りに確認した
- [ ] AIコメントがゼロのPRを「安全」と判断していない

### 重大度の判定

- critical（セキュリティ・データ整合性・課金・認証）→ **ブロッキング**
- それ以外のロジック不具合 → 要確認 / 採用推奨

---

## Stage 5: Design チェックリスト

機械的ヒントに留め、方向性は人間判断に委ねる。

- [ ] 責務分割: このメソッドはこのクラス/モジュールに置くべきか（断定せず選択肢を示す）
- [ ] APIの境界: 公開/内部の境界が適切か、漏れている内部実装がないか
- [ ] 依存方向: 循環依存、レイヤ違反（下位レイヤが上位を参照していないか）
- [ ] 関数・クラスの肥大化: 行数・引数の多さ（機械的ヒントとして提示）
- [ ] コードベース固有の制約: 読み取れた範囲で照合し、読めない部分は「ローカルルール確認が必要」と注記
- [ ] 「このパターンを増やすべきか減らすべきか」は**断定しない**。2人で合意すべきと伝える

---

## Stage 6: Architecture チェックリスト

レビューしない。事前ADR領域への侵入を検出して警告するだけ。

- [ ] 差分に以下が含まれるか確認（含まれれば「ADRで事前決定すべき」と警告）:
  - 新しいサービス境界・モジュール境界
  - 認証/認可の責任範囲の変更
  - データフロー・データストアの変更
  - デプロイ単位・インフラ構成の変更
- [ ] 既存ADRがあれば「ADRと整合しているか」だけを機械的に確認
- [ ] アーキテクチャ判断そのものは PR レビューで行わない

---

## Approve判断テンプレート

レビュー完了時にこのテンプレートを提示する。

```
## Approve判断: <対象PR/ブランチ>

[ ] Stage 1-2 自動ゲート通過
[ ] Stage 3 Style    : AI指摘に対応 or 却下理由を記録
[ ] Stage 4 Logic    : 仕様書と照合済み（AI指摘ゼロ箇所を含めて確認）
[ ] Stage 5 Design   : 責務分割に合意（必要ならペアで確認）
[ ] Stage 6 Architecture : 事前ADRと整合

ブロッキング指摘: N件
要確認（仕様照合待ち・ADR待ち）: M件

推奨: Approve可 / 条件付き / 保留
理由: <Logic・Designに未確認が残る場合は保留を推奨>
```

判定基準:
- ブロッキング指摘が1件でもあれば **保留**
- 仕様書を確認できていない、または Stage 4 に仕様未照合の指摘がある → **条件付き**
- すべて確認済み → **Approve可**
