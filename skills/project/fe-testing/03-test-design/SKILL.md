# テスト設計の判断

前提は `01-taxonomy`(分類)と `02-strategy-selection`(戦略)。
このスキルは対象を受け取り、**設計を判断して出力する手順書**。成果物は §9 のマトリクス。

```
入力受領 → S1 種別判定 → S2 粒度割当 → S3 静的解析の除外
        → S4 観点選定 → S5 観点の粒度配置 → S6 同居/分離判定
        → S7 優先順位・ROI → 出力(設計マトリクス)
```

---

## 入力受領

対象から読み取る。不足は推定し、推定である旨を出力に明記。粒度判定すら不能なほど曖昧な場合のみ、
ユーザーに1点だけ確認する。収集項目: 対象 / 依存(API・他UI・状態・ルーター) / 業務重要度 /
静的解析の状況 / 副作用(ネットワーク・ストレージ・描画計測)。

## S1 — 種別判定

| 種別 | 定義 | 例 |
| --- | --- | --- |
| A. 純粋ロジック | 依存のない関数・計算・状態遷移 | フォーマッタ、バリデータ、reducer |
| B. 独立フック/UI | 依存なし or モック可能な単一フック・コンポーネント | 表示専用 UI、独立フック |
| C. 複合 UI | 他コンポーネント/フックに依存して動作する UI | フォーム一式、リスト+行+操作 |
| D. 画面 | 複数の複合 UI + データ取得が統合された1画面 | 一覧/詳細画面 |
| E. 操作フロー | 画面をまたぐ操作の連鎖 | ログイン〜決済、登録ウィザード |

## S2 — 粒度割当(初期値)

| 種別 | 既定粒度 |
| --- | --- |
| A | ユニット |
| B | ユニット |
| C | インテグレーション |
| D | インテグレーション(重要時は一部 E2E) |
| E | E2E |

原則: 実アプリ UI の大半は C(複合)。自然とインテグレーションが最厚になる。
**E2E 抑制**: D/E でも E2E は最小限。クリティカルフローに限定し、他は統合粒度(API モック)で代替検討。

## S3 — 静的解析の除外

型・リンターで保証される検査をテスト対象から外す(無価値なテストの量産防止)。
- 値の型・必須/任意・列挙値・props 型不整合 → TypeScript が保証するならテストしない。
- 残すもの: 型で表現できない実行時の振る舞い・分岐結果・副作用・ユーザーから見た結果。

## S4 — 観点選定

| 観点 | 採用条件 | 不採用でよい条件 |
| --- | --- | --- |
| ロジック | 分岐・計算・状態遷移がある | 純粋表示で分岐なし |
| インタラクション | 操作で状態/表示が変わる | 操作要素がない静的表示 |
| スナップショット | 出力構造を機械的に固定したい | 変化頻繁で差分が無意味 |
| VRT | 見た目の退行が事業影響を持つ | 見た目要件が緩い内部画面 |
| a11y | アクセシビリティが要件/公共性が高い | 要件外かつ内部限定 |
| パフォーマンス | 体験要件が厳しい/重い描画 | 軽量で体感影響なし |
| クロスブラウザ | 複数ブラウザ対応が要件 | 対応ブラウザが単一 |

全観点を埋めようとしない。**ROI × 重要度** で取捨選択する。

## S5 — 観点の粒度配置(中核判断)

選定した各観点を、どの粒度に置くかを決める。同じ観点でも置く粒度は変わり得る。

| 観点 | 推奨配置粒度 | 理由 |
| --- | --- | --- |
| ロジック | ユニット | 依存を切れば最小・最速・最安定 |
| インタラクション | インテグレーション(主)/ユニット(単純操作) | 操作起点の振る舞いは複合 UI で価値が高い |
| スナップショット | ユニット〜インテグレーション | 出力構造を固定する単位に合わせる |
| VRT | ユニット(部品単位)or E2E/CT(画面全体) | 「部品の見た目」か「画面全体」かで分かれる |
| a11y | 静的/ユニット(構造)+ 統合(キーボード操作) | 構造は安価に、操作系は統合で |
| パフォーマンス | 部品=ユニット / 画面=E2E | 計測したい範囲に合わせる |
| クロスブラウザ | E2E | 実ブラウザ環境が必要 |

```
各観点について:
 [P1] 依存を切っても意味があるか? → Yes: ユニット粒度を優先検討(安定・高速)
 [P2] 実ブラウザ/実バックエンドが不可欠か? → Yes: E2E(重要フロー限定) / No: 統合(モック)
 [P3] 「部品単位」か「画面・フロー全体」か? → 部品: ユニット〜統合 / 全体: 統合〜E2E
```

## S6 — 同居 / 分離判定

**原則: 1テスト = 1観点(分離)**。混在すると失敗原因の切り分けが困難になり、片方の変更で壊れる。

同居を許す例外(すべて満たす場合のみ): 同じ粒度・同じ対象 / 一方が他方の前提として自然に連続 /
同居しても失敗原因が一意に特定できる。

| 組み合わせ | 既定 | 理由 |
| --- | --- | --- |
| ロジック + インタラクション | 分離 | 粒度も対象も異なる |
| インタラクション + 結果の表示確認 | 同居可 | 「操作→結果」は一連の振る舞い |
| インタラクション + キーボード a11y | 同居可 | 操作系 a11y は操作テストの延長 |
| 振る舞い + スナップショット | 分離 | 差分管理サイクルが異なる |
| 振る舞い + VRT | 分離 | VRT は画像差分の独立運用が必要 |
| 任意 + パフォーマンス計測 | 分離 | 計測の安定性が両立しにくい |

## S7 — 優先順位・ROI

基準 = **コストパフォーマンス × 業務重要度**。高い順:
1. クリティカルフロー(重要度が最優先で上書き)
2. ロジック × ユニット(低コスト・高安定、最初の一歩)
3. インタラクション × インテグレーション(トロフィーの主目的)
4. ロジック × インテグレーション
5. VRT / a11y(要件次第)
6. パフォーマンス / クロスブラウザ(要件のある画面に限定)

ROI が低い項目(型で済む検証、壊れやすいスナップショット乱用)は **根拠付きで明示的に落とす**。
落とした記録も設計の一部とする。

## 10. 実演(クーポン適用フォーム)

対象: 入力 → 適用ボタン → 割引後金額を表示。

1. S1: 入力・ボタン・表示が連動 → 種別 C(複合 UI)。
2. S2: 既定でインテグレーション。
3. S3: props 型・コード型は TypeScript が保証 → 対象外。
4. S4: ロジック(割引計算)=採用 / インタラクション(適用操作)=採用 /
   VRT=見た目要件が緩ければ不採用 / a11y=フォームなのでキーボード操作は採用候補。
5. S5: 割引計算は依存を切れる → ユニット。適用操作の振る舞い → インテグレーション。
6. S6: 割引計算(ユニット)と適用操作(統合)は分離。「押下→割引後金額の表示」は同居可。
   キーボード a11y は操作テストに同居可。
7. S7: 金額計算は誤りの事業影響大 → 最優先。次に適用操作の統合。
8. 出力: §9 のマトリクスに落とす。実装は 05(ロジック)・07(統合+モック)・09(a11y)へ。
