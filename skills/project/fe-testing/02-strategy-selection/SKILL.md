# テスト戦略の選定

前提知識は `01-taxonomy`。このスキルは **粒度の配分方針(=戦略)を1つ選ぶ** ための判断を行う。

## 戦略カタログ

### アイスクリームコーン型 — 原則アンチパターン
手動 / E2E を厚くし、下層を薄くする形。現代の E2E は不安定・低速・高メンテコストのため、
自動テストが品質保証の役割を果たせず開発生産性を損なう。**原則採用しない。**

### テストピラミッド型
ユニット最厚、次に統合、E2E は最小限。安定・高速・維持しやすく費用対効果が高い汎用戦略。

### テスティングトロフィー型(フロントエンド向け)
下から **静的解析 → ユニット → インテグレーション(最厚) → E2E**。
- 基底に静的解析を明示。TypeScript・リンターで事前検出できる範囲は ROI が極めて高い。
- 実アプリの UI は大半が複合(インテグレーション)であり、「ユーザー操作起点のテストに比重を
  置くべき」という思想から、インテグレーション層を最も厚くする。

---

## 選定フロー

```
[Q1] アイスクリームコーンになっていないか(手動/E2E依存・下層が薄い)?
        ├─ Yes → 是正対象。下層(静的解析/ユニット/統合)の拡充を最優先で計画
        └─ No  → Q2

[Q2] TypeScript 等の静的型付けが導入され機能しているか?
        ├─ Yes → トロフィー型が有力(静的解析層を戦略に明示できる)
        └─ No  → まず静的解析の導入自体を最優先課題に。困難ならピラミッド型ベース

[Q3] UI の実態は「複合 UI」主体か「独立ユニット UI/関数/フック」主体か?
        ├─ 複合 UI 主体 → トロフィー型(インテグレーション層を最厚)
        └─ ユニット主体 → ピラミッド型(ユニット層を最厚)

[Q4] 品質担保が必須な操作フロー(決済/認証等)があるか?
        ├─ Yes → 上記戦略に加え、その経路だけ E2E を例外的に優先配置
        └─ No  → 標準配分で進める
```

## 重要な前提

- 戦略は形状を強制するものではなく、配分の優先順位を示す指針。
- トロフィー型でも「ユニット UI/関数/フックが少ない」コードベースでは、粒度を問わず
  テストを充実させるだけで自然とトロフィー形状になる。
- どの戦略でも E2E は壊れやすく高コスト。**E2E はクリティカルフローに限定**し、
  それ以外は統合粒度(バックエンドをモック)で代替できないか先に検討する。

## 2026 年の実情を踏まえた補足

- Storybook(Vitest addon)や Playwright CT により「実ブラウザ × 隔離」での複合 UI テストが
  容易になった。これによりトロフィー型の「厚いインテグレーション層」を、遅い E2E ではなく
  高速なコンポーネントテストで構成しやすくなっている。
- 静的解析(TypeScript)が普及した現在、トロフィー型がフロントエンドの事実上の標準寄り。
  ただしレガシー構成やユニット主体のライブラリ的コードベースではピラミッド型が依然有効。

## 出力

選定結果として次を確定し、`03-test-design` に渡す。
- 採用戦略(ピラミッド / トロフィー)
- 最厚にする粒度
- E2E を許可するクリティカルフローのリスト
