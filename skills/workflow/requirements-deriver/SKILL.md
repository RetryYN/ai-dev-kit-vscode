# Requirements Deriver — 機能要件からの非機能要件導出

## 適用タイミング

このスキルは以下の場合に読み込む:

- 新規システム・新機能・ツールの設計に着手する時
- データベースのスキーマ・テーブルを設計する時（分離レベルの判断がここで固定されるため）
- システムプロンプトや設定値を「固定文字列」で書こうとしている時
- 機能要件・ユーザーストーリー・提供形態が文章として存在する時
- 上記に加え、「複数」「顧客」「組織」「テナント」「提供」「SaaS」「決済」「個人情報」「連携」「24時間」「大量」のいずれかが要件に出た時

---

## このスキルの目的

AIにコーディングを任せると、設計のデフォルトがシングルテナントの固定ツールに倒れる。AIは明示されたコンテキストの範囲で最短の「動くもの」を作るため、要件として渡されない非機能要件は存在しないものとして扱われる。テナント分離・可用性・セキュリティ境界のような横断的関心事は、コンパイルが通ってしまうがゆえに、欠落しても気づかれないまま事故になる。マルチテナント化やデータ分離の後付けは極端に高くつく層であり、最初に方針を決めておくかどうかが効いてくる。

このスキルは、コードを生成する前に「この機能要件からはどの非機能要件が立ち上がるか」を強制的に通す関所として機能する。AIが構造的にスキップする設計判断を、要件から逆算して外から与えることが役割である。

## L1 layer 接続点

本 skill は HELIX L1 要件定義 phase の核心として以下の位置に置かれる:

- **入力**: 機能要件 doc（L1 entry の要件記述、ユーザーストーリー、提供形態の記述）
- **出力**: 非機能要件 list（IPA × ISO 25010 二軸、R1〜R14 シグナル根拠付き）
- **L1 exit 条件**: 「ISO/IEC 25010:2023 9 特性網羅チェック実施済」かつ「要確認項目を確認リストとして提示済」
- **L1 → L2 接続**: 出力された非機能要件 list が L2 design-doc（workflow/design-doc）の入力に反映される

V-model 4 artifact 対応:
- **① 設計（L1 要件 / 非機能要件）** ↔ **③ 受入テスト設計**（別 doc、L8 受入の検証観点）
- 本 skill は ① 設計層（L1 非機能要件の導出）を担当する
- 対応する ③ テスト設計（受入テスト）は別 skill・別 doc で並行作成する（`helix/HELIX_CORE.md §設計⇔テスト対応` 参照）

---

## 入力は「要件」であって「対話」ではない

このスキルは原則としてユーザーに質問しない。提供形態・分離レベル・可用性などは、機能要件と非機能要件（サーバー要件・インフラ要件）にすでに書かれているか、そこから機械的に導けることがほとんどである。

動作はこうなる。まず機能要件・非機能要件のドキュメントを読み込み、後述の導出ルールを適用して非機能要件を導出する。要件に記載が欠けている項目だけを最後に確認リストとして提示する。要件が揃っていれば質問はゼロで方針が出る。AIが無自覚に固定化するのは、多くの場合「単に要件を読んでいない」だけである、という前提に立つ。

## 分類の二軸（両軸で扱う）

導出先である非機能要件は、二つの分類軸の両方でタグ付けする。役割を分けることで、現場で通る整理と網羅性の担保を両取りする。

### 主軸：IPA 非機能要求グレード（判断と根拠の軸）

> 出典: IPA「非機能要求グレード 2018」2018 年 4 月版（2018 改訂が最終 / 2019-03 利用ガイド第2版 / 2023 年頃 IPA アーカイブへ移管・事業終了。ISO 25010 とのマッピングは 2011 版ベース。後継版なし。日本 SI 実務では現役チェックリストとして利用継続）— https://www.ipa.go.jp/archive/digital/iot-en-ci/jyouryuu/hikinou/ent03-b.html

日本のシステム開発現場で事実上の標準として通る分類。要件定義・インフラ判断の根拠を出す主軸として使う。6 大項目は次の通り。

1. **可用性**（継続性・耐障害性・災害対策・回復性）
2. **性能・拡張性**（業務量・性能目標値・リソース拡張性）
3. **運用・保守性**（通常運用・保守運用・障害時運用・運用環境）
4. **移行性**（移行時期・移行方式・移行データ量・移行リハーサル）
5. **セキュリティ**（アクセス制限・データ秘匿・不正追跡／監視）
6. **システム環境・エコロジー**（システム制約・前提条件・適合規格）

### 副軸：ISO/IEC 25010 製品品質モデル（網羅漏れチェックの軸）

> 出典: ISO/IEC 25010:2023（2nd edition）Systems and software Quality Requirements and Evaluation（SQuaRE）製品品質モデル — 2011 版 8 特性から 9 特性へ改訂（Safety 追加 / Usability→Interaction Capability / Portability→Flexibility）。日本語訳は暫定（JIS X 25010:2025（IDT）が未発行のため、発行後に正式訳へ更新する）。

より普遍的でプロダクト品質寄りの 9 特性。導出結果に漏れがないかを潰すチェック軸として使う。英語正式名を正とし、日本語は暫定訳として扱う。

**機能適合性 (Functional Suitability) / 性能効率性 (Performance Efficiency) / 互換性 (Compatibility) / 相互作用能力 (Interaction Capability、旧 Usability) / 信頼性 (Reliability) / セキュリティ (Security) / 保守性 (Maintainability) / 柔軟性 (Flexibility、旧 Portability、Scalability を包含) / 安全性 (Safety、新規)**

> 関連標準: 2011 版 ISO/IEC 25010 は 2023 改訂で、製品品質モデル（25010:2023）/ 利用時品質モデル（ISO/IEC 25019:2023、旧 Quality in Use を独立化）/ 概論・用語（ISO/IEC 25002:2024）の 3 規格に分離された。本 skill の副軸は製品品質モデル 25010:2023 を使う。

### 両軸の使い方

導出した各非機能要件には、IPA 分類と ISO/IEC 25010 特性の両方のラベルを必ず付ける。IPA で「現場でどう根拠づけ、どこに費用と運用を割くか」を語り、ISO/IEC 25010 で「品質特性として漏れている観点はないか」を最後に照合する。

なお ISO/IEC/IEEE 42010:2022（Architecture Description）は非機能要件を viewpoint として記述する際の上位参照規格であり、L2 ADR 起票時に参照する（本 skill の主軸は IPA と ISO 25010:2023）。

**安全性 (Safety) の扱い**: 安全性は人・事業・財産・環境への危害回避を扱う 2023 版の新規特性。開発フレームワーク CLI 等のドメインでは通常「現れない（該当薄）」とし、本番影響・破壊的操作（rollback --apply / DB destructive op 等）のシグナルがある場合のみ「現れる」と判定する。R1〜R14 へ無理にマップしない。

## 中核：機能要件シグナル → 非機能要件 の導出ルール（R1〜R14）

このスキルの心臓部は判断軸そのものではなく、「機能要件のどのシグナルが、どの非機能要件を立ち上げるか」の写像である。要件文の中に左列のシグナルを見つけたら、対応する非機能要件・両軸ラベル・典型的な設計判断を引き当てる。

### R1. 複数の顧客・組織への提供（マルチテナント）

- **立ち上がる非機能要件**: テナント分離、障害の波及範囲（blast radius）、テナント別データ保持、テナント単位の認可境界
- **IPA**: 可用性 / セキュリティ｜**ISO 25010**: 信頼性 / セキュリティ
- **設計判断**:
  - データ分離レベルを三択から選ぶ。物理 DB 分離（サイロ: 分離最強・コスト高・テナント数でスケールしにくい）/ スキーマ分離（ブリッジ: 同一 DB 内でスキーマを切る中間）/ 行レベル分離（プール: 共有テーブルに `tenant_id` 列 + 行レベルセキュリティ、最もスケールするがフィルタの作り込み必須）
  - テナントコンテキストの取得元を一つに定める（JWT クレーム / IAM プリンシパル / サーバー側セッション）。**認可は必ずこの値を根拠にし、クライアント由来のセッション ID 等を認可根拠にしない**
  - 単一インスタンス前提のシステムプロンプト・設定の固定文字列化を禁止し、テナント変数の注入構造にする
  - オンボーディング・オフボーディング（テナント追加・解約時のリソース作成・削除）の自動化方式

### R2. 単一ユーザーだが将来テナント化の可能性がある

- **立ち上がる非機能要件**: 将来の分離コストの最小化
- **IPA**: 移行性 / セキュリティ｜**ISO 25010**: 保守性
- **設計判断**: 今はプール相当の単一構成でも、初期から `tenant_id` 列だけは持たせておく等の折衷で後付けコストを織り込む。「将来テナント化の可能性」が要件にある場合が最も判断を誤りやすいので、明示的に折衷案を出す

### R3. 単一ユーザー固定で提供形態の拡張予定なし

- **立ち上がる非機能要件**: 特になし（過剰設計の回避）
- **設計判断**: 堂々と固定構成で作る。マルチテナント化を検討しない、という判断もこのスキルが明示的に出力する。曖昧なまま無自覚に固定化するのとは区別する

### R4. 金銭・決済・課金を扱う

- **立ち上がる非機能要件**: データ整合性、監査証跡、決済セキュリティ、二重実行防止
- **IPA**: セキュリティ / 可用性｜**ISO 25010**: 機能適合性 / セキュリティ / 信頼性
- **設計判断**: トランザクション境界の設計、冪等キーによる二重課金防止、監査ログ（誰が・いつ・何を）、決済領域の規格適合（PCI DSS 等）の要否確認

### R5. 個人情報・機微情報を扱う

- **立ち上がる非機能要件**: コンプライアンス、データ最小化・削除、保存・通信の暗号化、アクセス制御
- **IPA**: セキュリティ｜**ISO 25010**: セキュリティ
- **設計判断**: 適用法令（個人情報保護法 / GDPR 等）の確認、保持期間と削除（忘れられる権利）のフロー、保存時・通信時の暗号化、最小権限のアクセス制御

### R6. 24 時間・365 日の利用、サービス停止が許されない

- **立ち上がる非機能要件**: 高可用性、無停止デプロイ、障害分離
- **IPA**: 可用性 / 運用・保守性｜**ISO 25010**: 信頼性
- **設計判断**: 冗長化（マルチ AZ / マルチリージョン）、ローリング / ブルーグリーンデプロイ、ヘルスチェックと自動復旧、目標稼働率に対する SLA 定義

### R7. テナントごとに SLA や可用性水準が異なる

- **立ち上がる非機能要件**: ティア別の分離方針
- **IPA**: 可用性｜**ISO 25010**: 信頼性
- **設計判断**: 全テナントを同一モデルに揃えず、上位ティアはサイロ、下位ティアはプール、といったハイブリッド / ブリッジモデルを選ぶ。可用性は分離レベルとハイブリッド採否の両方に効く入力として扱う

### R8. 大量データ・高同時アクセス・急なスパイク

- **立ち上がる非機能要件**: 性能効率、水平拡張性、ノイジーネイバー対策
- **IPA**: 性能・拡張性｜**ISO 25010**: 性能効率性
- **設計判断**: 水平スケール前提の構成、キャッシュ層、非同期処理・キュー、テナント・ユーザー単位のレート制限とクオータ

### R9. 外部システム・他社 API との連携

- **立ち上がる非機能要件**: 相互運用性、連携の信頼性、障害伝播の遮断
- **IPA**: 可用性｜**ISO 25010**: 互換性 / 信頼性
- **設計判断**: 冪等な連携設計、リトライとバックオフ、サーキットブレーカ、タイムアウト、連携先障害がこちらに波及しない隔離

### R10. リアルタイム性・低遅延が要件

- **立ち上がる非機能要件**: レイテンシ目標
- **IPA**: 性能・拡張性｜**ISO 25010**: 性能効率性
- **設計判断**: エッジ / CDN 配置、コネクション管理、同期処理範囲の最小化、レイテンシの数値目標と測定

### R11. 多デバイス・多 OS・多言語・多地域

- **立ち上がる非機能要件**: 柔軟性（旧 移植性）、相互作用能力（旧 使用性）、地域別の可用性
- **IPA**: システム環境｜**ISO 25010**: 柔軟性 / 相互作用能力
- **設計判断**: レスポンシブ / クロスプラットフォーム対応、国際化（i18n）、地域別リージョン配置とデータレジデンシ要件の確認

### R12. 既存システムからの移行・既存データの取り込み

- **立ち上がる非機能要件**: 移行性
- **IPA**: 移行性｜**ISO 25010**: 保守性
- **設計判断**: 移行方式（一括・段階）、データ変換とクレンジング、並行稼働期間、移行リハーサルと切り戻し計画

### R13. 監査・規制対象の業務、操作の追跡が必要

- **立ち上がる非機能要件**: 追跡可能性、ログ保持
- **IPA**: セキュリティ / 運用・保守性｜**ISO 25010**: セキュリティ
- **設計判断**: 構造化された監査ログ、改ざん耐性、保持期間、可観測性（メトリクス・トレース・ログ）の設計

### R14. 従量課金・レート制限のある外部リソースを利用

- **立ち上がる非機能要件**: コスト効率、レート制限への耐性
- **IPA**: 性能・拡張性 / 運用・保守性｜**ISO 25010**: 性能効率性
- **設計判断**: 使用量の計測と上限、コストの可視化、レート制限到達時のフォールバックとキューイング

## 実行フロー

1. 機能要件・非機能要件（サーバー要件・インフラ要件含む）のドキュメントを読み込む
2. 文中から導出ルール R1〜R14 のシグナルを抽出する
3. 各シグナルに対応する非機能要件を引き当て、IPA と ISO/IEC 25010 の両軸でタグ付けする
4. 各非機能要件を、具体的な設計判断（分離レベル・冗長構成・認証方式・データ保持方針など）まで展開する
5. ISO/IEC 25010:2023 の 9 特性を一周し、どのシグナルからも引かれなかった抜け観点がないか照合する
6. 要件に記載が欠けていて判断を確定できない項目だけを、確認リストとして提示する

## 原則

- **デフォルトに倒れさせない。** 提供形態・分離レベルを未検討のまま単一スキーマで進めない。固定でよいなら、固定でよいと明示的に判断を出す（R3）。
- **根拠を必ず示す。** どの非機能要件も、どの機能シグナルから導かれたかを紐づける。根拠のない要件を足さない。
- **要件に書いてあることを正とする。** 要件に存在しない項目を推測で盛らない。確定できないものは「要確認」として分け、勝手に決めない。
- **認可はクライアント由来の値を根拠にしない。** テナント・ユーザーの認可判断は、JWT クレームまたは IAM プリンシパルと、サーバー側で管理するマッピングを根拠にする。クライアント由来のセッション ID・ヘッダー値・クエリパラメータを認可根拠にすることを禁ずる。
