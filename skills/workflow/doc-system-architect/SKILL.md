# Doc System Architect — ドキュメント体系の設計

## 適用タイミング

このスキルは以下の場合に読み込む:
- 新規プロジェクト・リポジトリの立ち上げ時
- ドキュメントを書き始める時、または既存ドキュメントを整理・棚卸しする時
- 個別の設計ドキュメント（アーキテクチャ・非機能要件・運用手順など）に着手する時
- 引き継ぎ・オンボーディング資料を用意する時
- HELIX の G0.5 / L1 / L2 entry で「何を書くか」を確認する時

---

## このスキルの目的

「開発の記録としてどこまで書くべきか」には、両側に失敗がある。書かなすぎれば、なぜその設計にしたかが失われ、属人化し、引き継ぎも再現もできなくなる。書きすぎれば、すぐ陳腐化してメンテ負債になり、誰も読まない誤情報の山ができる。正しい量はプロジェクトの性質ごとに違い、固定の体系を全案件に当てると、小さなツールには過剰になり、大きな規制案件には不足する。

このスキルは、ドキュメント体系を二段で設計する。第一段は **変数判断**（プロジェクト特性から、書くべき種別と粒度を導出する）。第二段は **業界標準への整合**（実行時にその時点の標準・慣行を確認し、採用すべき標準とテンプレートに案件を合わせる）。固定の答えを埋め込むのではなく、判断とリサーチで毎回最適化する判断系スキルである。

---

## 第一段：変数判断 — 「どこまで書くか」を決める原理

### 最優先で残すのは Why

最も価値が高い記録は「なぜ（Why）」である。コードを読めば「何を（What）・どうやって（How）」は復元できるが、「なぜその構成を選び、何を却下したか」は書かない限り消える。後から最も復元しにくく、最も高くつくのが設計判断の根拠である。記録の優先順位:

**Why（判断の根拠・却下案・トレードオフ） > What（仕様・インターフェース・データモデル） > How（実装手順）**

How を厚く書くと陳腐化して負債になりやすい。How は原則コードと自動テストに語らせ、ドキュメントは Why と What に集中させる。

### 量を決める 4 変数

書くべき量は、ほぼ次の 4 変数で決まる。各変数を評価し、合算で粒度を決める。

1. **決定の不可逆性・影響範囲** — 後で覆せない／広く波及する決定ほど厚く残す。可逆で局所的な決定は薄くてよい。
2. **読み手** — 誰が将来読むかで密度が決まる（後述の読み手種別を参照）。
3. **変更頻度** — よく変わるものを詳細に書くと即陳腐化する。変わるものはポインタ（最新がどこを見れば分かるか）に留め、変わらないものだけ実体で書く。
4. **再現可能性の要否** — 監査・規制・引き継ぎ・障害復旧があるなら、記録は任意ではなく義務になる。

### 読み手の種別（変数 2 の展開）

読み手によって、必要な密度とフォーマットが変わる。プロジェクト特性から読み手を判定し、複数該当する場合はそれぞれに向けた記録を用意する。

- **将来の自分（単独・短命）** — 最小限。意思決定の要点とハマりどころのメモで足りる。
- **チーム・引き継ぎ先（人間）** — 散文中心。背景・意図・トレードオフを文章で。オンボーディングの導線を用意する。
- **AI エージェント（コンテキストとして読ませる）** — 構造化・機械可読寄り。曖昧さを排し、参照範囲・制約・発火条件を明示。SKILL.md やエージェント向けコンテキストファイルがこの層。
- **外部・監査・規制当局** — 規格準拠のフォーマットと追跡可能性。保持期間も定義する。

### 運用原則

- **変わるものはポインタ、変わらないものは実体。**
- **一次情報は一箇所だけ（Single Source of Truth）。** コードコメントとドキュメントで同じことを二重管理しない。
- **探索・実験中は重く書かない。** 結論が確定した時点で記録に起こす（確定までは軽いメモに留める）。
- **ドキュメントは Definition of Done に含める。** 後回しにすると永久に書かれない。少量を継続的に。

## 第二段：業界標準への整合 — 実行時に必ず確認する

固定のテンプレートを押し付けず、案件に合う標準を選び、その現行版・現行慣行に合わせる。下のレジストリは出発点であり、**適用前に必ず Web 検索でその時点の現行版・最新の慣行を確認して補正する**こと。標準は改訂され、慣行も移り変わるため、記憶のまま適用しない。

### 確認すべき標準レジストリ（出発点）

- **ISO/IEC/IEEE 42010:2022 (第 2 版)** — アーキテクチャ記述の国際標準。2022 年版が最新（System of Interest → Entity of Interest 一般化、Architecture Model → View Component に名称変更）。規制・大規模・公的案件で準拠が問われる（出典: iso.org/standard/74393、ieee.org standards/42010）。
- **arc42** — 「何を・どう文書化するか」を 12 章で答える実用テンプレート。ADR を含む。中〜大規模で人間向けに有効。quality.arc42.org で ISO 42010 との対応表も公開。
- **C4 モデル**（Simon Brown） — Context / Container / Component / Code の階層的アーキテクチャ図。図の粒度を読み手別に分ける。
- **ADR / Architecture Decision Record**（Nygard 構造） — 重要な決定を、動機・検討した選択肢・結果とともに 1 決定 1 ファイルで残す。Why を残す中核手段。
- **Diátaxis** — プロダクト／利用者向けドキュメントを Tutorial / How-to / Reference / Explanation の 4 象限に分類する（Learning vs Working × Practical vs Theoretical matrix）。ユーザー向けドキュメントの構成に使う（出典: diataxis.fr/start-here/）。AI エージェント向け SKILL.md との親和性も高い。
- **Keep a Changelog / Conventional Commits** — 変更履歴とコミットの標準。
- **The Twelve-Factor App** — 設定・依存・運用に関する慣行（クラウド／SaaS の運用記述に有効）。
- **Runbook / Playbook**（SRE 系の慣行） — 障害対応・運用手順。
- **README / CONTRIBUTING / オンボーディングガイド** — 最小構成の入口。
- **IPA 非機能要求グレード 2018** — 非機能要件を体系化した日本語標準（2018 年 4 月版が最新）。ISO/IEC 25010 とのマッピングが整備されており、相互利用が標準的（出典: ipa.go.jp/archive/digital）。非機能要件層には requirements-deriver スキルと組み合わせる。

### 整合の判断

- 小規模・単独・短命なツールに 42010 フルや arc42 全章は過剰。README + ADR 数枚で足りることが多い。
- 中〜大規模・チーム開発なら arc42 + C4 + ADR の組み合わせが標準的。
- 規制・監査・公的調達が絡むなら 42010:2022 準拠と追跡可能性・保持期間を明示。
- 利用者がいるプロダクトなら、開発者向け（arc42 / C4 / ADR）と利用者向け（Diátaxis）を分ける。
- AI エージェントに読ませる前提があるなら、人間向けとは別に機械可読なコンテキスト層（SKILL.md 等）を設ける。

## ドキュメント種別の地図と対応標準

開発記録はおおむね次の層に収まる。各層を、上の変数判断で「書くか／どの粒度か」を決め、対応標準にマッピングする。

| 層 | 内容 | 対応する標準・形式 | 主な読み手 |
|---|---|---|---|
| 意思決定 | なぜこの選択をしたか、却下案、トレードオフ | ADR（Nygard）、arc42 ch.9 | チーム・将来の自分 |
| 設計 | アーキテクチャ、データモデル、IF、非機能要件 | 42010:2022、arc42、C4、（非機能は requirements-deriver） | チーム・AI エージェント |
| 仕様 | 機能要件、ユーザーストーリー | 要求記述の標準、課題管理 | チーム |
| 運用 | デプロイ手順、障害対応、監視 | Runbook、12-factor | 運用者 |
| 知識 | ドメイン知識、用語集、オンボーディング | README、CONTRIBUTING、Diátaxis | 新規参加者 |
| 変更履歴 | リリース・変更の記録 | Keep a Changelog、Conventional Commits | 全員 |
| AI 向けコンテキスト | エージェントに読ませる指示・制約・発火条件 | SKILL.md、エージェント向けコンテキストファイル | AI エージェント |

## V-model / HELIX layer mapping

本スキルはメタ層（体系設計）として L1〜L3 全域で参照される。個別 doc の作成は後続スキルに委譲する。

| HELIX layer | 本スキルの役割 | 後続 doc 作成スキル |
|---|---|---|
| L1 要件定義 | 受入ドキュメント種別の決定・体系設計 | workflow/requirements-handover |
| L2 全体設計 | アーキテクチャ記述標準の選択（42010 / arc42 / C4）・ADR 方針決定 | workflow/design-doc |
| L3 詳細設計 | D-API / D-DB / D-CONTRACT 粒度の確認 | workflow/design-doc |
| L8 受入 | 受入 doc の種別・保持期間の最終確認 | workflow/verification |

## HELIX 体系内の責務境界

本スキルは **メタスキル**（ドキュメント体系の設計判断）であり、個別 doc 本体の作成スキルとは責務が分離している。

| スキル | 守備範囲 | 本スキルとの関係 |
|---|---|---|
| **doc-system-architect（本スキル）** | ドキュメント体系の **設計判断**（何を / どこまで / どの粒度で書くか） | メタ層。個別 doc 作成の前に必ず通る |
| workflow/design-doc | L2/L3 個別設計書本体（D-API / D-DB / D-CONTRACT / D-STATE）の作成 | 本スキルの adoption 後に呼ばれる個別 doc 作成スキル |
| common/documentation | README / ADR / 技術文書テンプレートと品質チェック | 本スキルの推奨に従って個別 doc を作成する |
| workflow/requirements-handover | 要件曖昧・引き継ぎ時の確認 protocol | 入力段スキル。本スキルより前に呼ばれることがある |
| **workflow/requirements-deriver（姉妹スキル）** | 機能要件 → 非機能要件導出（IPA 非機能要求グレード × ISO/IEC 25010） | **本スキルが呼び出す子スキル**（非機能要件層を持つ場合） |
| workflow/adversarial-review | doc の adversarial check | 本スキル出力後のレビュー段階で呼ばれる |

使い分けルール:
- **ドキュメント体系の設計（何書くか決める）** → 本スキル
- **個別 doc の本文作成** → workflow/design-doc / common/documentation
- **非機能要件層の生成** → workflow/requirements-deriver（本スキルが呼ぶ）

## 実行フロー

1. プロジェクトの性質を把握する（規模・寿命・チーム / 単独・利用者の有無・AI エージェントが読むか・規制 / 監査の有無・技術スタック）。要件ドキュメントがあれば読み取り、無い項目だけ後で確認する。
2. 第一段の変数判断を適用し、各ドキュメント層について「書くか／粒度／読み手」を決める。
3. 第二段として、対象ドメイン・スタックに対応する現行のドキュメント標準・慣行を Web 検索で確認し、レジストリを最新に補正する。
4. 採用する標準を選び（過剰・不足を避ける）、各層を標準テンプレートにマッピングする。
5. 非機能要件の層がある場合は requirements-deriver を呼んで生成する。
6. 各ドキュメントの更新タイミング（いつ・何をトリガーに更新するか）を定める。
7. 出力フォーマットに従って、ドキュメント体系の設計案を提示する。要件に記載がなく確定できない項目は確認リストに分ける。

## 出力フォーマット

設計結果は必ず次のテンプレートで出力する。

```markdown

## 1. 前提として読み取ったプロジェクト特性
- 規模 / 寿命 / 読み手 / 規制有無 / スタック / AI エージェントの利用 ...

## 2. 採用する業界標準（および採用しない標準とその理由）
- [標準名]: 採用／不採用、根拠。Web 確認した現行版・最新慣行を併記。

## 3. 書くべきドキュメント一覧
| ドキュメント | 層 | 書く理由（4 変数のどれが効いたか） | 粒度 | 準拠標準/テンプレート | 更新タイミング |
| --- | --- | --- | --- | --- | --- |
| ... | ... | ... | ... | ... | ... |

## 4. 書かないと判断したもの（過剰回避）
- [候補]: なぜ今は不要か（可逆・局所・読み手不在 等）

## 5. 要確認（要件に記載がなく確定できない項目）
- [項目]: 何が決まれば確定するか
```

## 原則

- **両側の失敗を避ける。** 書かなすぎ（知識喪失・属人化）と書きすぎ（陳腐化・負債）の中間を、変数判断で根拠づけて選ぶ。
- **記憶のまま標準を適用しない。** 標準は改訂される。適用前に現行版と最新慣行を Web で確認する。
- **過剰設計を明示的に却下する。** 「書かない」という判断も根拠付きで出力する（出力フォーマットの第 4 節）。
- **Why を最優先で残す。** 却下案とトレードオフを含め、判断の根拠を最初に確保する。
- **確定したものだけ記録に起こす。** 探索中は軽いメモ、確定時に体系へ反映する。
