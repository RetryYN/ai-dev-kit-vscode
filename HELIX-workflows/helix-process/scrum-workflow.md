# Scrum HELIX ワークフロー

## 概要

Scrum は、ユーザーと要件をすり合わせながら反復的に開発するモード（アジャイル Scrum）。スプリント単位で機能（インクリメント）を作り、ユーザーのフィードバックで要件を継続的に調整する。作るものは概ね決まっているが、要件をユーザーと合わせながら固めて進めたい場合に使う。

## 業界標準との関係

> 注: スクラムガイドに準拠する。ロール（プロダクトオーナー / スクラムマスター / 開発者）、イベント（スプリント / スプリントプランニング / デイリースクラム / スプリントレビュー / スプリントレトロスペクティブ）、作成物（プロダクトバックログ / スプリントバックログ / インクリメント）。

## 入口判定

| 状況 | Scrum を使う理由 |
|---|---|
| 作るものは概ね明確だが要件をユーザーと合わせたい | 反復しながら要件を固める |
| ユーザーフィードバックで継続調整したい | スプリントごとにレビューで反映する |
| 早く動くものを見せて方向を確認したい | インクリメントを反復的に届ける |

要件・設計・契約が最初から確定しているなら Forward HELIX、成立するか未確定なら Discovery、既存資産の逆引きなら Reverse。

## 基本フロー（スプリント反復）

```
プロダクトバックログ
   → スプリントプランニング
   → 開発（デイリースクラムで日次同期）
   → スプリントレビュー（ユーザーと要件すり合わせ）
   → スプリントレトロスペクティブ
   → インクリメント（機能完成）
   ↺ 次スプリントへ反復
```

## 大規模実装の unitized Forward（L4 統一 → per-unit micro-Forward）

大規模サース・複雑設計で、実装サイズが大きい increment は一枚岩で L5–L7 を通すと unit が粗くなる。
**基本設計（L4）までは統一して Forward で降ろし、実装が大きいときは unit 単位に分割して
詳細設計（L5）⇒機能設計（L6）⇒実装（L7）の micro-Forward を細かく刻む**。

```
L4（基本設計：統一・単一で凍結）
  ├─ unit A: L5 ⇒ L6 ⇒ L7（micro-Forward・pair_closure で閉じる）─┐
  ├─ unit B: L5 ⇒ L6 ⇒ L7 ────────────────────────────────────┤→ 単一 V-model DB へ rejoin（L8/L9 統合）
  └─ unit C: L5 ⇒ L6 ⇒ L7 ────────────────────────────────────┘
```

- **L4 統一**: 境界・コンポーネント分割・契約は L4 で単一凍結し、unit はこの分割から導出する。
- **per-unit micro-Forward**: 各 unit = 縦スライス1本。自分の L5⇒L6⇒L7 と対の検証（L7 単体 / L8 結合）を持ち、
  unit ごとに独立検証してから次へ。
- **収束（絶対原則）**: 各 unit の L7 closure は統一 L4 設計へ rejoin し、単一 V-model DB に収束する。
  unit-Forward は枝であって代替でない（HELIX_CORE §0/§1）。
- **共有状態は直列化**: 共有ファイル・共有スキーマを touch する unit は直列、独立 unit は並列
  （並列規律は CLAUDE_RUNTIME_ADAPTER §2「並列8・衝突判定」と地続き）。

> 設計詳細・未確定の設計問題（unit 境界の正式定義 / unit 間依存の Forward 表現 / discovery 駆動 scrum との
> ステージ関係）は [docs/design/D-SCRUM-UNITIZED-FORWARD.md](../../docs/design/D-SCRUM-UNITIZED-FORWARD.md)（draft）に置く。
> 本節は実証済みコアのみを正式化し、未確定点は seed doc 側で confirm してから追補する。

## Vモデル体系への昇華フロー（重要）

スクラムで作った機能（インクリメント）は、最終的に Forward（Vモデル L0–L14）のドキュメント体系に昇華する。スクラムの速さ（反復・フィードバック）と Vモデルの厳格さ（ドキュメント体系・トレーサビリティ）を両立させるための接続フロー。

```
スクラム反復開発 → 機能（インクリメント）完成
   ↓ ドキュメント化（Reverse fullback を活用）
完成機能から成果物を起こす（F0–F4: evidence / contracts / as-is review / handover checklist / routing）
   ↓ Vモデル体系へ統合
L1 要求定義 / L3 要件定義 / L4–L6 設計 / L8–L9 テスト の各工程ドキュメントに整える
```

### 昇華の手順

1. スプリントで機能（インクリメント）が完成する。
2. `helix reverse fullback`（完了実装から文書整合と handover checklist を作る）でドキュメント化する。
3. 起こしたドキュメントを Forward の L0–L14 各工程ファイルの枠組み（`helix-process/L*.md`）に整理する。
4. 以後その機能も Vモデルのドキュメント体系（双方向 trace・ゲート）で管理する。

### 昇華先の対応

| 完成機能から起こす内容 | Vモデル昇華先 |
|---|---|
| 確定した要求・要件 | L1 要求定義 / L3 要件定義 |
| 実装された設計（方式・機能・データ） | L4 基本設計 / L5 詳細設計 / L6 機能設計 |
| 実装済みのテスト | **L7 単体テスト** / L8 結合テスト / L9 総合テスト（**L6↔L7** / L5↔L8 / L4↔L9 の対で同時凍結） |
| 運用・受入・文書整合 | L11–L14 |

これにより、スクラムで先に動くものを作っても、最終的に Vモデルの正式なドキュメント体系に乗り、トレーサビリティが確保される。

> **Forward 引き戻し規律（共通）**: `helix reverse fullback` 経由の昇華は [forward-return-discipline.md](forward-return-discipline.md) を**必須適用**する（fullback が Reverse 側の片肺をそのまま継承しないため）。固有点: 昇華先に **L6↔L7（単体）** を含め、L6 機能設計を昇華したら対の L7 単体テスト設計を同時凍結する。

## 起票する PLAN kind

完成機能の文書化は Reverse の `fullback` kind（F0–F4）を起票し、L0–L14 体系へ昇華する。逸脱と kind の対応は deviation-plan-map.md を参照。
